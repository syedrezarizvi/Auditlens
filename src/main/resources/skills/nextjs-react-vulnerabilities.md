---
name: nextjs-react-vulnerabilities
description: Test Next.js and React applications for framework-specific flaws: middleware-only authorization bypass, Server Actions reachable without authorization, secrets in __NEXT_DATA__, dangerouslySetInnerHTML and javascript: URL XSS, image optimizer SSRF, source map exposure, and outdated framework versions.
---
Scope: only the in-scope target. Use captured traffic first. Send no new requests unless the pentester has approved network actions, and keep every replay to a minimum.

1. Fingerprint. Look for X-Powered-By: Next.js, /_next/static/ assets, id="__NEXT_DATA__" in HTML, and the Next-Action header on POST requests. Record which routes are server-rendered pages, route handlers (/api/...) and Server Actions. Use list_endpoints and get_message; do not guess routes.
2. Middleware authorization (highest impact). Pick a protected page or API route that returns a redirect or 401/403 when unauthenticated. Replay it with remove_headers ["Cookie","Authorization"] and then with the added header x-middleware-subrequest set to a middleware path from the app's own routes (only if approved). A 200 with real protected content where the unmodified request was refused is a candidate authorization bypass. Confirm with two refs (refused baseline, bypassed response) and the version evidence.
3. Server Actions. A POST carrying a Next-Action header invokes a server function. Check whether it works with the unauthenticated session (remove Cookie and Authorization) and whether it accepts other users' object identifiers seen in captured traffic. Do not invent action IDs; reuse only the ones captured. A Server Action that returns protected data without a session is a finding.
4. Hydration data. In the __NEXT_DATA__ JSON, look for keys named token, secret, password, apiKey, privateKey, internal hostnames or whole records the page does not render. Quote only the key names and redact the values in the report.
5. React XSS sinks. In client JavaScript, search for dangerouslySetInnerHTML and for href or src values built from URL parameters. A reflected value that reaches a sink unsanitised, and that is not HTML-encoded in the response, is a candidate. Treat a JSON content type or a value inside a text node as a likely false positive.
6. Image optimizer. For /_next/image?url=..., test only that the upstream is restricted to the app's own allow-listed hosts (remotePatterns). Do not probe internal addresses or cloud metadata endpoints; report the absence of host restriction as a candidate and let the pentester decide on further testing.
7. Source maps. If a script ends with a sourceMappingURL comment, check whether the .map file is publicly served (one GET, same origin). An accessible map is a disclosure finding; the reveal of source code is the impact.
8. Versions. A version is only confirmed from a fingerprint in captured traffic (build IDs, package names in bundles) or from an advisory the pentester supplies. Do not state a version from memory. Compare with the vendor advisory and mark it as needing confirmation.

Evidence rules: a finding needs a baseline ref and a manipulated or observed ref. Mark confidence firm only when protected content is returned without authorization or a sink is confirmed to receive attacker input. Give the middleware and Server Action findings the severity of the data they expose, not of the framework.
